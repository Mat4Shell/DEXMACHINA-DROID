# DEX MACHINA // DROID

DEX MACHINA // DROID is the Android module of DEX MACHINA, a family of application security analyzers. It takes an Android package (APK, XAPK, APKS or AAB) and is meant to produce a security analysis that a penetration tester or a security analyst can act on, starting with static analysis and later extending to dynamic analysis.

Every file DROID opens is treated as potentially hostile. The parsers for the archive structure, Android binary XML, resource tables, DEX files and the APK signing block are being written for this project in Rust, with no unsafe code, bounded reads and explicit resource limits, so that a crafted application cannot act on the machine of the person analyzing it.

## Project status

DROID is in early development. The repository contains the Cargo workspace and its continuous integration, with one crate per area of the analysis: archive reading, binary XML and resources, DEX, signatures, the manifest model, reporting, and the `droid` command-line tool. The `droid` binary only answers `--version` and `--help` for now. Nothing here is ready for real use, and interfaces will change without notice until a first release is published.

The first parser is the ZIP container reader of `droid-archive`. It reads the central directory the way Android's own ZIP library does, so that the analysis covers the application Android would actually install, and it reports every construction that Android rejects, or that Android reads differently from a general-purpose ZIP tool, as a typed anomaly with a stable code. These differences are a common anti-analysis technique: a fake encryption flag, an unknown compression method that Android reads as stored, local headers that disagree with the central directory, duplicate names, data prepended or appended to the archive, or entries hidden from one reader or the other. Android itself does not read every entry the same way: the resource loader, ART for DEX files, the native library installer and the JAR signature verifier react differently to some of these tricks, so each anomaly names the component whose reaction it describes, and is reported once more for any other component that reacts differently. DEX files that ART never loads, because a number is missing in the `classes.dex`, `classes2.dex`, `classes3.dex` sequence that ART follows, are reported too: their code is visible to tools that read every DEX file, but not to the application's class loader.

Some constructions go further than misleading an analysis tool, and attack the device that installs the application. An entry whose name is exactly 65535 bytes long, the longest a ZIP archive can hold, and either starts with `lib/` or ends with `.bc`, triggers CVE-2026-58995, published in the Android Security Bulletin of November 2026 and fixed in the 2026-11-01 security patch level: the native library installer computes the size of the name in a 16-bit integer that wraps to zero, copies the name past the end of its buffer, and crashes while installing the application on devices without the fix. DROID reports it as `zip.entry.name_length_overflow`, for the native library installer, with the `exploit` impact, which marks constructions that trigger a published Android vulnerability on unpatched devices and ranks above an archive that Android merely refuses. It is reported only when Android's ZIP library actually hands the entry to the installer, that is when the name is valid and the local header agrees with the central directory.

Entries are only ever read in memory, never extracted to disk, under configurable limits on the number of entries, the size of the central directory, the uncompressed size of each entry and of the whole archive, and the compression ratio. Entry names are not limited, since the format already bounds them, but unusually long names are reported.

## Building and testing

DROID is built with stable Rust. The exact toolchain is pinned in `rust-toolchain.toml`, so with [rustup](https://rustup.rs) installed, the right compiler and components are selected automatically when you run Cargo from the repository. Build the whole workspace with `cargo build --workspace --locked`, and run the test suite with `cargo test --workspace --locked`. The command-line tool can then be started with `cargo run --bin droid -- --help`.

The continuous integration also checks formatting with `cargo fmt --all --check`, runs Clippy with `cargo clippy --workspace --all-targets --locked -- -D warnings`, and checks dependency licenses, security advisories, duplicate versions and sources with [cargo-deny](https://github.com/EmbarkStudios/cargo-deny) through `cargo deny check`. Running these commands locally before opening a pull request avoids a round trip with the CI. Contribution guidelines are in `CONTRIBUTING.md`.

The parsers are also fuzzed with [cargo-fuzz](https://github.com/rust-fuzz/cargo-fuzz), which needs a nightly toolchain. Each fuzzing harness is a separate Cargo workspace that is never part of the product. For the ZIP reader, run `cargo +nightly fuzz run zip_archive -- -dict=zip.dict` from `crates/droid-archive/fuzz`. The starting corpus is generated by the same code as the integration tests and is never committed: `DROID_FUZZ_SEEDS_DIR=crates/droid-archive/fuzz/corpus/zip_archive cargo test -p droid-archive --test fuzz_seeds -- --ignored` writes it. The `Fuzz` workflow runs every target each night, and on demand from the Actions tab, with a dated nightly toolchain and a corpus kept from one run to the next in the GitHub Actions cache. It never runs on pull requests and is not required to merge; when it finds a failing input, the run fails, its summary shows the input in base64, and the input is attached to the run as an artifact kept for 7 days.
